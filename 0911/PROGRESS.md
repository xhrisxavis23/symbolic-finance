## KST 00:20 — 종목군 분석 준비: 두 가지 발견

### 발견 1 — 호가 단위표를 외워 쓰면 틀린다

종목군을 LOBFrame 논문처럼 **상대 틱 크기**(스프레드가 평균 몇 틱인가)로 나누려면
틱 크기가 정확해야 한다. 기억에 의존하지 않고 데이터에서 쟀다
(무작위 160개 파일, 1~5호가 인접 가격 간격의 가격대별 최빈값).

```
가격대        최빈 간격 (상위 3)
<2천          1원 77%,  2원 10%,  3원 4%
2천~5천       5원 83%,  10원 10%, 15원 3%
5천~2만       10원 52%, 5원 31%,  20원 6%
2만~5만       50원 52%, 5원 24%,  10원 5%
5만~20만      100원 45%, 5원 37%, 200원 3%
20만~50만     500원 99%
≥50만         5원 100%
```

가격대별 최빈값은 호가 단위표(1·5·10·50·100·500원)와 맞는다. 그런데 **높은 가격대에
5원 간격이 24~37% 섞여 있고 50만원 이상은 100% 5원이다.** 이 표본은 전체 3,726 파일에서
뽑아 ETF 등이 섞였으므로 **ETF 의 다른 호가 규칙**일 가능성이 크다 — 단, 추정이다.
2,507개 주식 종목만으로 다시 재면 확인된다(아래 측정의 `tick_share` 로 드러난다).

**판정:** 표를 코드에 박지 않는다. **종목마다 실제 인접 호가 간격의 최빈값을 틱으로
쓴다.** ETF 규칙이든 가격대 경계를 넘나드는 종목이든 자동으로 맞는다. 최빈값이 차지하는
비율(`tick_share`)을 함께 저장해 틱 판정이 불확실한 종목을 걸러낼 수 있게 한다.

### ⚠ 50만 행은 조기 종료의 부작용이다

50만 행 DeepLOB 이 양쪽 이웃보다 낮다. "조기 종료 걸림" 으로 기록됐지만, 평가 곡선이
최선(80 epoch) 뒤 일시 하락했다가 **회복하던 중에 인내 10회가 소진돼** 멈췄다
(… 0.0112 → 0.0116 → 0.0121 → 0.0123, 상승 중에 종료). 에폭 예산을 늘려도 같은 자리에서 멈춘다.

**"조기 종료가 걸렸다" 는 "수렴했다" 가 아니다.** 잘림(예산 소진)을 고쳤더니 그 아래에
또 하나가 있었다.

- 지금 도는 200만·500만·1000만 지점도 인내 10 이라 같은 부작용이 있을 수 있다.
  **곡선이 끝나면 이상 지점을 인내 30 으로 다시 잰다.**
- 종목군 분석의 교사는 기동 전에 인내를 30 으로 올렸다(사전등록 부록 D).

## KST 00:50 — 시험 운전이 GPU 설정 버그를 잡았다. 그리고 내 GPU 판단이 거꾸로였다

종목군 실행(`group_run.py`)을 종목 36개·30 epoch 로 시험 운전했다. 적재 84/84 블록,
표본 선별, 윈도우 생성까지 정상이었는데 **교사를 `cuda:1` 에 올리는 순간
`CUDA error: invalid device ordinal` 로 죽었다**(`groups/smoke_group_run.fail1_cuda_ordinal.log`).
이대로 본 실행을 걸었으면 적재에 수십 분을 쓰고 같은 자리에서 죽었을 것이다.

### 원인

```
~/.bashrc 82행   export CUDA_VISIBLE_DEVICES=GPU-2c93540d-…   # ollama: GPU1 고정
파이토치가 보는 GPU 수   1
물리 GPU0  GPU-dcd70e26-…  15 MiB    비어 있음
물리 GPU1  GPU-2c93540d-…  49.5 GB   표본 크기 곡선 측정이 사용 중. ollama 서비스도 떠 있음
```

- 사용자 셸 설정이 GPU 를 **물리 GPU1 한 장**으로 고정한다. 여기서 띄운 모든 프로세스는
  GPU1 만 보고 그것을 `cuda:0` 으로 부른다. 그래서 `cuda:1` 은 존재하지 않았다.
- **내 판단이 거꾸로였다.** "곡선이 GPU0 을 쓰니 종목군은 GPU1" 이라 했는데, 곡선은 이미
  물리 GPU1 에 있었고 GPU0 이 비어 있었다. GPU 번호를 확인하지 않고 가정했다.
- **GPU1 은 사용자가 ollama 용으로 고정해 둔 장치다.** 곡선 측정이 모르고 그 장치의 49.5GB 를
  쓰고 있다. 지금 ollama 에 올라간 모델은 없지만, 요청이 오면 부딪힐 수 있다.

### 수정

- `~/.bashrc` 는 사용자 설정이므로 건드리지 않는다.
- 종목군 실행은 **기동할 때만** `CUDA_VISIBLE_DEVICES` 를 물리 GPU0 으로 지정하고 장치는 `"cuda"`.
- **`GROUP_GPU_UUID` 를 받아 보이는 장치의 UUID 와 대조하고, 다르면 즉시 멈춘다.**
  조용히 엉뚱한 GPU 에 올라가 다른 실행과 겹치는 일을 막는다 — 이 프로젝트의 결함은 늘
  "오류 없이 조용히 틀린" 종류였다.

## KST 00:55 — 교사는 전체 배치 학습이다. "3일 전체 학습" 은 이대로는 불가능하다

`gpu_eval/deeplob_gpu.py::fit` 을 읽었다:

```python
inputs = torch.tensor(self._standardise(X), dtype=torch.float32, device=self.device)  # 학습 데이터 전체를 GPU 로
def train_step():            # 매 epoch: 전 행에 대해 순전파·역전파 한 번
    latent = self._encode(inputs) ...
```

**미니배치가 없다.** 1 epoch = 전체 행에 대한 경사 한 번. 곡선 측정은 200만 행에서 GPU 49.5GB 를 쓴다.

### 귀결 (메모리 투영은 지금 실측 중 — 곱한 추정으로 확정하지 않는다)

- **곡선의 500만·1000만 지점은 98GB 한 장을 넘어 메모리 부족으로 죽을 가능성이 크다.**
- **지시 1 "3일 전체 학습" (저마찰층 4,570만 행) 은 전체 배치로는 물리적으로 불가능하다.**
- 종목군 분석(200만 행, GPU0 한 장)은 영향 없다.

### 계획

3일 전체를 학습하려면 **미니배치 학습**으로 바꿔야 한다. 짚어둘 것 두 가지:

1. 이것은 모델 구조가 아니라 **학습 절차**의 변경이다. 그런데 "epoch" 의 의미가 바뀐다
   (지금: 1 epoch = 경사 1회 / 미니배치: 1 epoch = 경사 수백~수천 회). 표본 크기 곡선·종목군
   분석의 전체 배치 결과와 **직접 비교되지 않는다.**
2. 그래서 3일 전체에 쓰기 전에 **같은 200만 행·같은 시드에서 미니배치가 전체 배치와 비슷한
   선택 종목 R² 에 닿는지 먼저 검증**한다. 허용 오차는 검증을 돌리기 전에 정한다.

측정: `scale/measure_gpu_memory.py` — 메모리는 값이 아닌 모양에만 달려 있으므로 무작위 배열로
10만~120만 행을 재서 선을 긋고, 200만 행 관측치(49.5GB)와 대조해 투영이 맞는지 확인한다.

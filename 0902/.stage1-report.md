## 1. 만든 파생 열 — 계획서 §3 S3 무차원 그룹 사전 대응표

전부 `sd/derived.py`에 등록. 이름 → Catalog AST 하나만 두고, 수치는 그 AST를
`framework.contract.ExpressionRuntime`으로 평가해서 얻는다(별도 numpy 구현 없음).
등록 시점(`_register`)에 `catalog.infer_expression_type()`으로
`dimension == "dimensionless"`를 강제한다 — import 시점에 전부 검사된다.

| 파생 열 | AST | 사전 항목 | 왜 |
| --- | --- | --- | --- |
| `ofi_over_qbar_5` | `ratio(ofi_depth_5, rolling_mean(bid_queue_depth_at_l1, w=100))` | 정규화 주문흐름 OFI/Q̄ | 태스크 지시 필수 예시. L2 법칙(Cont–Kukanov–Stoikov)의 인수 |
| `ofi_l1_over_qbar` | `ratio(ofi_cks_1, rolling_mean(bid_queue_depth_at_l1, w=100))` | 정규화 주문흐름 OFI/Q̄ | 원형 CKS OFI(최우선호가만)를 같은 Q̄로 |
| `ofi_over_qbar_10` | `ratio(ofi_depth_10, rolling_mean(bid_queue_depth_at_l1, w=100))` | 정규화 주문흐름 OFI/Q̄ | 1~10호가까지의 깊은 OFI |
| `mid_return_5t_over_spread` | `ratio(mid_return_5t_bps, spread_bps)` | 정규화 가격변화 ΔP/s | 태스크 지시 필수 예시 (시간 스케일 5t) |
| `mid_return_20t_over_spread` | `ratio(mid_return_20t_bps, spread_bps)` | 정규화 가격변화 ΔP/s | 태스크 지시 필수 예시 (20t) |
| `mid_return_100t_over_spread` | `ratio(mid_return_100t_bps, spread_bps)` | 정규화 가격변화 ΔP/s | 태스크 지시 필수 예시 (100t) |
| `microprice_velocity_over_spread` | `ratio(microprice_velocity, spread_bps)` | 정규화 가격변화 ΔP/s | 1틱 momentum — mid_return류와 다른 시간 스케일의 ΔP |
| `bid_l1_depth_over_qbar` | `ratio(bid_queue_depth_at_l1, rolling_mean(bid_queue_depth_at_l1, w=100))` | 정규화 심도 Q_k/Q̄ | OFI/Q̄와 분모(Q̄)를 공유하는 상태(state) 짝 |
| `ofi_depth_5_zscore` | `rolling_zscore(ofi_depth_5, w=100, min_obs=20)` | z-정규화 상태 (x-μ)/σ | OFI를 외부 스케일(Q̄) 대신 자기 분포로 정규화 |
| `microprice_velocity_zscore` | `rolling_zscore(microprice_velocity, w=100, min_obs=20)` | z-정규화 상태 (x-μ)/σ | 가격변화를 외부 스케일(spread) 대신 자기 분포로 정규화 |

**총 10개.** `window=100`은 정본 프레임워크가 이미 못박은 "직전 100틱" 관례
(`framework.contract.ROLLING_QUANTILE_WINDOW = 100`,
`THRESHOLD_ROLLING_PRIOR_100_TICKS_QUANTILE`)를 그대로 재사용한 것 —
다른 값을 골랐다면 같은 질문("직전 몇 틱")에 두 번째 답을 만드는 셈이다.
`min_observations=20`은 그 20%.

### 사전 항목 중 파생을 만들지 않은 것과 이유

| 사전 항목 | 처리 |
| --- | --- |
| 큐 불균형 `I` | 이미 `book_imbalance`·`queue_imbalance_best`로 존재 |
| 마찰비 `s/(s+c)` | 이미 `spread_to_round_trip_cost_ratio`로 존재 |
| 정규화 스프레드 `s/δ` | **제외.** `δ`(KRX 호가단위)는 가격대별 계단함수라 Catalog에 없다. 손으로 계산하면 두 번째 진실 원천이 된다 |
| 심도 집중도 `Q_1/ΣQ_k` | 이미 `ask/bid_depth_concentration`으로 존재 |
| 서명 체결 강도 | 이미 `signed_aggr_flow_20/100`으로 존재 |
| 깊은 층 불균형 | 이미 `deep_depth_imbalance_6_10`으로 존재 |
| 불균형 강도비 α/β (Hawkes) | **제외.** 계획서가 명시적으로 "E2 전용"이라 적었다 |

`microprice_dev_bps / spread_bps`도 일부러 넣지 않았다 — Catalog 자신의
`feature_use_policy('microprice_dev_bps').note`가 "= book_imbalance/2"라고
실측으로 적어 둔 **알려진 정확한 중복**이다. 넣었으면 D14가 경고한 바로 그
아핀 중복 축을 하나 더 만드는 것이었다.

## 2. 컴파일러 왕복 — `to_catalog._walk` 폴백

```python
if name in _catalog.FEATURES:
    return {"op": "primitive", "primitive_id": name}
if name in _derived.DERIVED:
    return _derived.get(name)          # 등록된 AST 그대로, deepcopy
raise TranslationError(...)
```

Catalog가 항상 우선이다. 이름 충돌은 `sd/derived.py`의 `_register()`가
import 시점에 막는다(`catalog.FEATURES`/`catalog.ALIASES`와 겹치면
`ValueError`). 실측 확인:

```
>>> to_catalog.translate(sympy.Symbol("ofi_over_qbar_5"))
{'op': 'ratio', 'numerator': {'op': 'primitive', 'primitive_id': 'ofi_depth_5'},
 'denominator': {'op': 'rolling_mean',
                 'input': {'op': 'primitive', 'primitive_id': 'bid_queue_depth_at_l1'},
                 'window': 100, 'time_basis': 'tick'},
 'zero_policy': 'nan'}
```

전에는(ROADMAP.md가 인용한 실측) `TranslationError: Catalog 에 없는 feature`
였다.

## 3. `check.py` — `condition_problem` 검사

`static_check`에 `_reject_banned_condition_targets()`를 추가했다. **`compare`
/`crossover` 노드의 `input`을 negate/absolute wrapper만 통과시켜 벗긴 뒤,
남는 것이 단일 `primitive`면 그 feature 이름으로 `catalog.condition_problem()`을
부른다.** 다른 것과 결합된 순간(`add`/`multiply`/`ratio`/...)부터는 "재료"로
보고 검사하지 않는다 — `condition_problem`의 docstring이 명시한 구분
("다른 식의 재료로는 쓸 수 있다")을 그대로 코드로 옮겼다.

`compare_values`는 리터럴 임계가 없어(두 표현식을 서로 비교) 검사 대상에서
의도적으로 뺐다 — 테스트로 그 결정을 고정해 뒀다(`test_static_check_does_not_
police_compare_values_targets`).

## 7. 남은 우려

1. **파생 열 자체가 새로운 (거의) 중복 축을 만들 수 있다.** 검증 run에서
   `e001`(`tanh(bid_l1_depth_over_qbar)`)과 `e003`(`sqrt(Abs(bid_l1_depth_
   over_qbar))`)이 동일한 원장을 냈다. 원인: `bid_l1_depth_over_qbar`는
   `quantity/quantity` 비율이라 **항상 0 이상**이고, 그 위에 얹은 `tanh`도
   `sqrt(Abs(·))`도 음이 아닌 정의역에서는 둘 다 순증가라 같은 분위수 컷을
   고른다. `catalog.condition_problem`은 **Catalog에 등록된 named feature**
   에만 정의돼 있어 우리가 새로 만든 합성 AST(`ratio(...)`)의 부호·범위까지는
   보지 못한다 — 이 조합은 어떤 기존 방어망도 잡지 못했다. 후속으로 파생
   열마다 "실제 값 범위(항상 비음수인가)"를 기록해 두고, 그런 열에는 `Abs`
   래퍼를 SR 탐색 사양에서 배제하는 것을 고려할 만하다(지금은 손대지 않음 —
   범위 밖).
2. **naive SR 백엔드의 컴파일 성공률(50%)은 대표성이 없다** — 계수 없는
   템플릿 후보라 PySR(2단계) 도입 후 다시 재봐야 한다(report.md 자체가 이미
   이 경고를 찍는다).
3. **`ofi_over_qbar_*` 세 depth 변형(1·5·10)이 서로 얼마나 독립적인지는
   아직 안 봤다** — 실제 KRX 데이터에서 상관을 재는 것은 이 태스크 범위
   밖이지만, 2단계(PySR) 탐색 예산을 아끼려면 사전에 재는 게 좋다.
4. **`sd/derived.py`의 `zero_policy="nan"` 선택**은 이 저장소의 "0은 관측을
   지어내는 것" 원칙과 일치하지만, 정본 `catalog.condition_problem`처럼
   분모가 자주 NaN(예: 세션 첫 100틱)이 되는 시간대에 관한 별도 감사는
   하지 않았다.
5. 이번 검증 run은 6종목·per-stratum 1로 작게 돌렸다 — 표본이 늘면 다른
   파생 열(`ofi_over_qbar_5`·`ofi_l1_over_qbar` 등)도 SR 후보에 등장할
   가능성이 높지만, 이번 run 하나로는 "10개 전부가 후보에 나타나는가"까지는
   확인하지 못했다(그 중 5개 이름이 실제로 등장했고 계산 실패는 0건이라는
   것만 확인했다).

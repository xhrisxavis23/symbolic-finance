## 0. 한 줄 요약

PySR 백엔드가 실제로 붙었고, 정본 배관 끝까지 갔다. 컴파일 성공률(F7의 첫 진짜 측정)은 **27% → 53%**(나눗셈 지원 전/후, 6종목·시드 0·완전히 같은 교사)로 나왔다 — 다만 이 상승이 "나눗셈 후보가 살아남아서"는 **아니다**(§6에서 실측으로 확인). 두 값 다 **20% 미만이 아니므로 F7 폐기선에는 걸리지 않지만**, 6종목·`ShallowMLP` 교사라는 슬라이스 규모에서 잰 것이라 본 실험(2,570종목·DeepLOB)의 값을 예측하지 않는다.

## 1. 착수 조건 두 건

### 조건 1 — Ruling R20: `abs(product) != 1` 이 `sympy.Float` 에서 깨진다

**진단 재확인 (수정 전, 이 세션에서 직접 실측).**

```python
>>> abs(sympy.Float(-1.0)) != 1
True                            # 틀림 — 크기가 정확히 1인데 "다르다"고 나온다
>>> abs(sympy.Float(-1.0)) - 1 != 0
False                           # 맞음
>>> sympy.Float(1.0) == 1       # 정수 리터럴
False                           # sympy 1.14 의 실제 동작 — 놀랍지만 사실이다
>>> sympy.Float(1.0) == 1.0     # 부동소수 리터럴
True
```

원인은 sympy 1.14 의 `Float.__eq__` 가 파이썬 `int` 와 `float` 를 다르게 다루는 것 — `!=` 는 내부적으로 같은 `__eq__` 를 타므로 같은 함정에 걸린다.

**수정 (`sd/compile/to_catalog.py`):**

```python
if not outermost and abs(product) - 1 != 0:   # 이전: abs(product) != 1
```

`product - 1` 뺄셈은 이 타입 불일치를 피해 가고, `== 0` 비교는 Float/Integer 어느 쪽이든 정확하다.

**검증 (직접 실측, 수정 후):**

```
translate("book_imbalance - queue_imbalance_best")        → OK   (정수 -1)
translate("book_imbalance - 1.0*queue_imbalance_best")     → OK   (부동소수 -1.0, 수정 전엔 거부됨)
translate("book_imbalance + 2.0*queue_imbalance_best")     → 거부 (여전히 올바르게 거부 — |c|=2 이므로)
```

**실제 PySR 출력에서도 이 경로가 살아 있다** — 검증 run 의 `candidates.json` 에 `queue_imbalance_best*0.14208119 - 1*1.0729966` 같은 후보가 실제로 나왔고, `strip_monotone` 이 offset 을 벗긴 뒤 `translate` 가 성공적으로 (check 단계에서 별개 이유로 탈락하긴 하지만) 컴파일 단계를 통과했다.

**테스트** (`tests/test_compile_translate.py`): `test_depth_sign_flip_via_subtraction_with_float_coefficient_is_still_translatable`, `test_depth_float_coefficient_of_negative_one_point_zero_is_translatable`, `test_depth_float_coefficient_other_than_unit_magnitude_is_still_rejected` — 3개 신규.

### 조건 2 — 심볼 제약의 명시 검증 (`sd/sr/pysr_backend.py::_extract_candidate`)

```python
used = {str(s) for s in expr.free_symbols}
if not used <= set(allowed_names):
    unknown = sorted(used - set(allowed_names))
    return _ExtractOutcome(None, {"reason": "free_symbols_outside_feature_names",
                                  "expr": str(expr), "unknown_symbols": unknown}, None)
```

`NaiveBackend` 는 `lambdify` 가 모르는 심볼에 object dtype 을 내고 `float()` 캐스트가 `TypeError` 를 던지는 것을 `except Exception` 이 우연히 삼켜서 걸러진다 — **우연한 가드**다. 여기서는 `free_symbols ⊆ allowed_names` 를 직접 비교해서 아니면 즉시 버리고, `PySRBackend.diagnostics["discarded"]` 에 사유(`unknown_symbols`)를 남긴다. `fit()` 은 탈락 개수를 `[pysr]` 로그로도 찍는다.

이 검증이 "우연한 가드"로 퇴화하지 않았는지는 `sympy.lambdify` 자체를 스파이로 바꿔 "범위 밖 심볼이면 `lambdify` 가 호출되지도 않는다"를 직접 증명하는 테스트로 확인했다 (`test_free_symbol_check_short_circuits_before_any_lambdify_attempt`) — §7 뮤테이션 표 참고.

## 2. PySR 백엔드 (`sd/sr/pysr_backend.py`)

### 연산자 집합 — `to_catalog.translate` 왕복 실측 (2차 수정 반영, 최종)

| 연산자 | 최종 | 근거 |
| --- | --- | --- |
| `+` `-` `*` | ✅ | `Add`/`Mul` |
| `/` | ✅ **(2차 수정으로 추가)** | 처음엔 제외했다 — `to_catalog._walk` 의 `Pow` 분기가 지수 `-1` 을 전부 거부해서(Catalog 에 `ratio` 연산자가 `zero_policy` 까지 갖고 있는데 매핑이 없어서). 코디네이터 지시로 `Mul` 처리에 분자/분모 분리를 추가해 `a/b → ratio(a,b,zero_policy="nan")` 로 옮기게 고쳤다 (§4). 여전히 분자가 상수뿐인 나눗셈(`2/x`)과 `-1` 이 아닌 음수 지수(`x**-2`)는 거부한다 |
| `sqrt` | ✅ | `Pow(x,1/2)` → `sqrt`. 밑이 음수여도 컴파일은 거부하지 않는다(Catalog `sqrt` 에 양수 도메인 정적 강제 없음) — 실행 시 `nan`, 하류 유한값 필터가 흡수 |
| `tanh` | ✅ | `tanh` 노드 |
| `abs` | ✅ | `absolute` 노드 |
| `square` | ✅ | PySR 내장 sympy 매핑이 `x**2` 를 냄 → `multiply(x,x)` |
| `log` | ❌ | `to_catalog._walk` 명시적 거부 ("인수 양수성 미보장") — 우회 불가 |
| `sign` | ❌ | `to_catalog._walk` 에 대응 노드 없음 |

최종적으로 PySR 에 주는 것: `binary_operators=["+","-","*","/"]`, `unary_operators=["sqrt","tanh","abs","square"]`. `maxsize=20`(계획서 상한, 생성자가 초과 시 `ValueError`), `complexity_of_constants=2`.

### 결정론 vs 병렬성

`deterministic=True`(기본값) → `parallelism="serial"`, `random_state=seed`. `deterministic=False` 로 바꾸면 `parallelism="multithreading"`. 어느 쪽인지는 `PySRBackend.diagnostics["deterministic"]/["parallelism"]` 과 `report.provenance(sr_deterministic=...)` 산출물(`provenance.json`, `report.md` "SR 결정론" 행)에 남는다. `Candidate` 자체(5-필드 공유 계약)에는 넣지 않았다.

### 가중치 — PySR 손실에 명시적으로 전달

```python
model.fit(X_fit, y_fit, weights=w_fit, variable_names=list(names))
```

`weights=` 를 빼는 뮤테이션을 실제 PySR 로 검증했다(§7) — deterministic 모드에서 `X`·`y`·`seed` 를 고정하고 `w` 만 바꿨을 때, `weights=` 가 빠지면 두 호출이 **바이트 단위로 동일한** Pareto front 를 낸다는 것을 직접 확인했다.

### `in_sample_score` — 수식을 직접 평가, 부호 맹목 결함 미상속

`NaiveBackend._score` 는 후보를 lstsq 로 다시 스케일·절편을 맞춰 채점한다 — `-2*x` 도 `2*x` 와 똑같이 잘 맞아 부호에 맹목이다. `PySRBackend` 는 `weighted_r2(y, raw, w)` 를 **수식이 낸 값 그대로** 적용한다 (`_extract_candidate`). `test_score_is_sign_aware_unlike_naive_backends_external_refit` 이 이 차이를 직접 확인한다: `y=2x0` 에 대해 `2*x0` 는 점수 > 0.99, `-2*x0` 는 점수 < -0.9.

### `complexity` — PySR 값이 아니라 `complexity_of` 로 재계산

두 백엔드가 같은 자로 재야 Pareto 비교가 성립한다. PySR 값과 다르면 `PySRBackend.diagnostics["complexity_mismatches"]` 에 (식, PySR 값, 재계산 값) 을 남기고 `[pysr]` 로그로 건수를 찍는다. 실측: 나눗셈 지원 전 15개 중 7개, 지원 후 15개 중 11개가 불일치했다 — PySR 자신의 복잡도 척도(연산자별 가중치, 상수 가중치 2)와 `sympy.preorder_traversal` 노드 수는 애초에 다른 자이므로 불일치 자체는 정상이다.

## 4. 추가 지시 1 — 나눗셈 → `ratio` (`sd/compile/to_catalog.py`)

### 왜 막혀 있었는가, 왜 뚫을 수 있었는가

sympy 는 `a/b` 를 `Mul(a, Pow(b, -1))` 로 표현한다. 기존 `_walk` 의 `Pow` 분기는 지수가 `{1/2, 2}` 일 때만 받고 그 외(특히 `-1`)는 전부 거부했다 — "역수는 ratio/divide 로 명시해야 분모 0 정책이 붙는다"는 메시지 **자체가 해법을 말하고 있었다**: Catalog 의 `ratio` 연산자(`numerator`, `denominator`, `zero_policy`)가 정확히 그 정책을 이미 갖고 있는데 `_walk` 가 그것을 만들어 내는 경로가 없었을 뿐이다. 연구계획서 §3 의 "실행 문법 제약" 표는 "`/` → `divide`/`ratio` 로 그대로 옮겨진다"고 적었지만, 이건 **실제 코드와 달랐다** — 계획서 작성 시점의 구멍이었다.

### 구현

`Mul` 의 비상수 인자를 훑어 `Pow(base, -1)` 꼴을 "분모"로, 나머지를 "분자"로 가른다(실측: `x/(b*c)` 는 sympy 에서 분모마다 별도 `Pow` 노드로 남아 하나로 안 뭉친다 — 그래서 리스트로 모아 `multiply` 로 접는다). 분모가 있으면:

```python
{"op": "ratio", "numerator": <분자 AST>, "denominator": <분모 AST>, "zero_policy": "nan"}
```

**여전히 안 되는 것 둘**은 의도적이다:
- **분자가 상수뿐인 나눗셈**(`2/x`, `1/x`) — Catalog 에는 산술 안에 수치 리터럴을 놓을 노드가 없다는, 이 파일 전체를 관통하는 제약이 여기서도 적용된다. 명시적으로 거부하고 이유를 남긴다.
- **`-1` 이 아닌 음수 지수**(`x**-2`) — 여전히 거부. `ratio` 로 표현 가능한 것은 정확히 `-1` 뿐이다.

### `zero_policy` 선택: `"nan"` (`RATIO_ZERO_POLICY` 상수, `to_catalog.py`)

| 후보 | 안 쓴 이유 |
| --- | --- |
| `"zero"` | DESIGN.md §7 이 이미 정확히 이 모양의 사고를 막아 뒀다 — `labels.build` 는 CENSORED 를 0 으로 채우지 않고 마스크로 제외한다("0 으로 채우면 나쁜 거래만 사라진다": 음수여야 할 사건이 무해한 0 으로 둔갑해 나쁜 쪽만 안 보이게 지워진다). 분모 0/결측을 0 으로 채우면 같은 왜곡이 재현된다 |
| `"reject"` | 실데이터에서 분모가 정확히 0/NaN 인 틱이 하루 중 단 하나만 있어도 `ExpressionRuntime.evaluate` 가 예외를 던져 그 진입식 전체가 재생 단계에서 죽는다 — PySR 이 어떤 feature 를 분모로 고를지 미리 알 수 없어 너무 부서지기 쉽다 |
| **`"nan"`(채택)** | 분모 0/결측 틱은 NaN 이 되어 하류(마스크·`weighted_r2`·`select.summarise`)가 이미 하는 방식대로 관측 불가로 제외된다 — `labels.build` 원칙과 정확히 같은 모양. `sd/derived.py` 의 기존 파생 열 10개 전부 이미 `zero_policy="nan"` 을 쓴다 — 새 관례가 아니라 기존 관례를 따른 것 |

### 검증 — 코디네이터 지시 케이스 전부 + 실제 배열 평가로 의미 보존 확인

```
a/b                    → OK   ratio(a, b)
a/(b*c)                → OK   ratio(a, multiply(b,c))
(a*b)/c                → OK   ratio(multiply(a,b), c)
2/a (최외곽)             → 거부  "분자가 상수뿐이다"
sa + 2/a (깊이)          → 거부  같은 이유, 깊이에서도 동일
a/b + c                → OK   add(c, ratio(a,b))
a**-2                  → 거부  "지원하지 않는 지수: -2"
1/a (홀로 선 역수)        → 거부  Pow 분기 전용 메시지("분자가 상수 1 뿐")
```

**의미 보존**: `test_ratio_translation_matches_independently_computed_division` 이 합성 호가 데이터 위에서 `ExpressionRuntime.evaluate(ratio_ast)` 를 두 feature 를 직접 얻어 numpy 로 나눈 값과 대조한다(300틱, 분모 0 제외 전부 일치). `(a*b)/c` 형태도 별도 테스트로 확인.

**PySR 연산자에 `/` 재추가.** `BINARY_OPERATORS = ("+","-","*","/")`.

## 5. 추가 지시 2 — `juliacall` 신호 처리

`PYTHON_JULIACALL_HANDLE_SIGNALS=yes` 를 `ensure_pysr_env()` 에 추가했다.

**실측 결과 — 경고는 사라지지 않는다.** juliacall 소스(`juliacall/__init__.py`)를 직접 읽었다: "torch was imported before juliacall" 경고는 `"torch" in sys.modules` 만 보고 **무조건** 뜬다 — `opt_handle_signals`(=`PYTHON_JULIACALL_HANDLE_SIGNALS`) 는 이것과 무관한 **다른** 경고(다중 스레드 신호 처리 크래시 위험)를 위한 설정이다. 실제로 재현했다:

```python
import torch                              # 교사(ShallowMLP)가 먼저 로드
config.ensure_pysr_env()                  # PYTHON_JULIACALL_HANDLE_SIGNALS=yes 배선됨
import pysr                               # → UserWarning: torch was imported before juliacall... (여전히 뜬다)
```

`run_slice.py --sr-backend pysr` 검증 run 양쪽(나눗셈 전/후) 모두에서 이 경고가 실제로 떴다 — 사라진 척하지 않는다.

**남은 위험.** `run_slice.py` 는 모듈 최상단에서 `from sd.teacher.shallow import ShallowMLP`(torch 기반)를 이미 임포트해 두고, S1 교사 학습이 끝난 뒤에야(S3 단계) `pysr` 를 지연 import 한다 — 즉 이 실행 순서 자체(torch 먼저) 는 구조적으로 남아 있다. `PYTHON_JULIACALL_HANDLE_SIGNALS=yes` 는 juliacall 자신이 권하는 **크래시 완화책**(신호 처리로 인한 세그폴트 위험 감소)이지 이 경고의 근본 원인(임포트 순서)을 고치지 않는다. **완전한 해결은 임포트 순서 자체를 바꿔야 한다**(예: `--sr-backend pysr` 를 고르면 teacher 임포트보다 먼저 `pysr` 를 예열) — 이번 세션에서는 하지 않았다. 근거: (1) 코디네이터 지시가 "환경변수를 함께 설정하라"였지 임포트 재배선을 요구하지 않았다, (2) 실제로 이 순서로 두 번의 전체 검증 run(각 5~6분, PySR fit 포함)이 세그폴트 없이 끝까지 돌았다 — 지금 당장 크래시가 나는 상태는 아니다, (3) 임포트 재배선은 "SR 백엔드를 고르지 않았는데도 매번 Julia 예열 비용(~100초)을 낼 것인가"라는 별도의 트레이드오프를 만드는, 이 태스크 범위를 넘는 구조 변경이다. **세그폴트가 실제로 나면 그때 다시 본다** — 지금은 위험을 기록만 한다.

**테스트**: `test_ensure_pysr_env_also_sets_juliacall_signal_handling`, `test_ensure_pysr_env_does_not_override_an_existing_signal_handling_choice` — 뮤테이션 검증 완료(§7).

## 9. 남은 우려

1. **`torch`/`juliacall` 임포트 순서 경고는 해소되지 않았다** (§5). 지금까지 크래시는 없었지만 구조적 위험은 남아 있다 — 세그폴트가 실제로 관측되면 임포트 순서 재배선(teacher 지연 임포트 + `--sr-backend pysr` 일 때 `pysr` 선(先)예열)을 검토해야 한다.
2. **나눗셈 지원의 실질 효과는 이 슬라이스에서 검증되지 않았다** — 번역 자체는 합성 데이터로 의미 보존을 확인했지만, 실제 검색이 살아남는 `ratio` 후보를 찾는지는 시드·규모에 따라 다를 수 있다(§6). 더 큰 `niterations`·더 많은 종목에서 다시 재봐야 한다.
3. **`complexity_of_constants=2` 를 포함해도 여전히 상수 표류(constant drift)가 보인다** — 예: `(ask_depth_concentration + queue_imbalance_best + tanh(...))*0.1101432` 류가 항 하나만 미세하게 바꾼 채 여러 복잡도 단계에 나타난다. Pareto front 실질 다양성이 낮을 수 있다 — 5단계에서 `duplicate_signal_groups` 로 실측해야 한다.
4. **`log`·`sign` 은 여전히 없다** — 계획서가 "스케일 압축"·"방향 대칭 구조" 명분으로 요구했던 것들인데, `to_catalog` 확장 없이는 못 준다. `log1p` 로의 치환이나 `sign`→`compare`+`all`/`any` 우회는 이번 세션 범위 밖이다(계획서도 "구현돼 있지 않다"고 실측됨).
5. **PySR `fit()` 이 매번 ~280초** — 대부분 Julia JIT 워밍업(첫 `import pysr` 자체가 이미 ~22초, 첫 `fit()` 은 그 위에 추가로 더 걸린다). 5단계 규모(전종목 반복 fit)에서는 이 고정비가 누적될 수 있다 — 워밍업된 프로세스를 재사용하는 구조(예: 장시간 실행되는 워커)를 그때 고려해야 한다.
6. **`s1_gate_ignored=True` 로 검증했다** — 게이트 자체는 실제로 통과했지만(3검사 전부), `--ignore-gate` 를 준 채로 돌렸다는 사실이 두 run 의 provenance 에 남아 있다.
